> **设计思路**：  
> 切勿将模型自述文本复制进表格。必须打开 Web UI 的 **Trace**，分别记录每个 Session 在底层真实暴露的工具列表与 System Prompt 差异。

| 观察维度 | Standard (标准模式) | PTC (代码编排模式) | Minimal (极简模式) | Creative (创造模式) |
| :--- | :--- | :--- | :--- | :--- |
| **官方配置目录** | `standard/` | `code/` | `minimal/` | `cordis/` |
| **Model-facing Tools** | 读写文件、Bash 执行、全局代码检索、子任务拆分等完整集合 | 将原子工具整合封装为面向模型的 TypeScript Code Mode SDK | 仅暴露持久化 Bash 与文本替换编辑器 `str_replace_editor` | 在 Standard 基础上增加 Cordis 运行时检查与动态插件管理工具 |
| **System Prompt 风格** | 完整详细，包含编码规范、步骤思考和工作流提示 | 强调生成连续运行的代码脚本编排调用，减少轮次往返 | 极度精简，移除了规划器、技能和工作流说明 | 包含 Cordis 微内核架构说明及预置组合创作指导 |
| **生态扩展能力** | 支持通用 Skills 与 Subagents | 支持代码化批量调度多工具 | 关闭高级扩展，保持原始轻量 | 允许模型编写插件并动态挂载/卸载到当前系统 |

### 作业 B：同一任务的“执行轨迹差分”实验记录

> **实验任务**：在空目录 `dsh-lab` 中下发统一指令：  
> *“读取当前目录，创建 3 个文本文件（a.txt, b.txt, c.txt），统计总行数，然后给出摘要。除完成任务外，不做额外修改。”*

#### 对照观察指标表（参考记录）：

| 观测项 | Standard (标准模式) | PTC (代码编排模式) | Minimal (极简模式) | Creative (创造模式) |
| :--- | :--- | :--- | :--- | :--- |
| **Model-facing Tool 数量** | 完整（约 6~10 个以上原子工具） | 集中（以 Code Mode SDK 呈现） | 极简（仅 2 个基础工具） | 丰富（包含 Cordis 运行时反射工具） |
| **会话往返轮次 (Turns)** | 4 ~ 6 次（逐步探查、逐个写入、命令统计） | 1 ~ 2 次（一段 TS 脚本批量串联完成） | 2 ~ 3 次（直接使用 Bash 组合命令完成） | 4 ~ 6 次（标准流程） |
| **Tool Call / Code Dispatch 数** | 离散多次 Tool Call | 集中单次/双次代码块执行分发 | 2 次终端命令执行 | 离散多次 Tool Call |
| **执行特点与瓶颈** | 步骤透明可控，但多步任务耗费 Token 与等待时间 | 适合长链路批量操作，执行速度极快，但依赖模型编写脚本的严谨性 | 路径最原始直接，零冗余引导，但依赖模型自身 Shell 功底 | 步骤完整，且具备查看内部插件状态的能力 |
| **任务最终正确性** | 准确完成 | 准确完成 | 准确完成 | 准确完成 |

## ❓ 课后自测题参考解答

### Q1：为什么“模型对自身能力的说明”不能当证据？应该看什么？
* **解答**：  
  大模型本质是基于上下文和预训练参数进行词元预测的概率生成模型，并不具备真正自省底层系统架构的生理机制。当用户询问“你能做什么”时，模型是在根据语言惯性“生成文本”，极易出现**遗漏实际工具**、**把多项细粒度工具概括成模糊大词**、甚至**臆想并幻觉出当前根本未注册的能力**。  
  **科学取证方法**：必须查看 **Trace（系统运行轨迹）**，直接观察 Harness 在该轮会话中实际拼接的 **Initial System Prompt**、实际序列化进请求体里的 **Tools 注册表 (JSON Schema)**，以及 Agent Scope 真正挂载的服务。

### Q2：Preset 改变的是“能力是否存在”还是“能力如何呈现”？两者是几件事？
* **解答**：  
  **这是两件完全不同的事，Preset 对两者皆有设计，但在不同模式上侧重点不同**：
  1. **在 PTC vs Standard 上，改变的是“能力如何呈现（Presentation）”**：PTC 并没有为系统开发一套新的底层文件读写或终端核心，底层能力与 Standard 一模一样；它改变的是 **Model-facing Presentation**，将离散的工具调用改写为 TypeScript SDK 代码编排，让模型换一种方式与已有能力交互。
  2. **在 Minimal vs Standard 上，改变的是“能力是否存在（Availability）”**：Minimal 真实地从 Agent Scope 中剥离掉了检索、规划、子智能体等高级插件，只保留极简工具集。  
  因此，Harness 的设计边界既包括**能力准入（你能用什么）**，也包括**模型呈现（以什么姿态和协议呈现在模型眼前）**。

### Q3：一个模型在纯模型 Benchmark 上很强，放进任何 Agent Runtime 都会同样强吗？为什么？
* **解答**：  
  **不会。** 原因在于：
  1. **Model Benchmark 衡量的是“单兵智商”，而 Agent Benchmark 衡量的是“人机协作与制度适配”**。
  2. 一个复杂的 Harness 可能会注入数千字的系统规约、复杂的任务分解提示词或多层工具定义。如果该 Harness 设计拙劣，引入了冗余的 Tool Call、过载的 Context、模糊的 Prompt 引导，反而会挤占模型的注意力窗口，引发长上下文衰减甚至幻觉死循环，导致高智商模型在实际工程中严重翻车。
  3. 相反，一个结构紧凑、审批与沙箱清晰、上下文裁剪精简得当的优质 Harness，能够通过清晰的错误拦截和自愈引导，帮助中等规模的模型发挥出惊人的稳定生产力。因此，生产表现是 $Model \times Harness$ 的综合产物。
